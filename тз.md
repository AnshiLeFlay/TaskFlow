## ТЕСТОВОЕ ЗАДАНИЕ ДЛЯ FULLSTACK РАЗРАБОТЧИКА (AI_NATIVE)

### Контекст
Вам необходимо разработать **MVP** системы управления проектами и задачами – **«TaskFlow»** – с возможностью создавать **канбан-доски** с настраиваемыми статусами и правилами переходов (workflow). Приложение должно быть доступно через три интерфейса: **REST**, **gRPC** и **WebSocket**. Вся бизнес-логика должна быть покрыта тестами (unit, интеграционные, e2e). Код должен следовать принципам **DDD** и **TDD**, а также содержать спецификации (OpenAPI/Swagger, protobuf) и инструкции для AI-агента (папка `.opencode`).

### Бизнес-требования (функциональные)

1. **Аутентификация и авторизация**
   - Пользователь регистрируется/входит через **Keycloak** (используйте адаптер для Go).  
   - В приложении проверяется валидность JWT-токена, полученного от Keycloak.  
   - Роли: `admin` (создатель проекта), `member`, `viewer`.

2. **Проекты**
   - Пользователь может создавать проект (становится его владельцем).  
   - В проект можно добавлять других пользователей с указанием роли.

3. **Канбан-доски**
   - Каждый проект содержит **одну или несколько досок** (например, "Основная", "Бэклог").  
   - У каждой доски есть **набор статусов** (колонок) – пользователь может создавать, редактировать, удалять статусы (название, порядок).  
   - Для каждой доски можно настроить **правила переходов** между статусами:
     - например, с `To Do` → `In Progress` разрешено только автору задачи;
     - с `In Progress` → `Review` разрешено только если есть комментарий;
     - с `Review` → `Done` разрешено только владельцу проекта.  
   - Правила должны быть **конфигурируемыми** (хранятся в БД) и применяться при попытке изменить статус задачи.

4. **Задачи**
   - Задача привязывается к доске и имеет текущий статус.  
   - При создании задачи указываются: название, описание, исполнитель, дедлайн.  
   - Перемещение задачи между статусами происходит через REST-запрос, при этом **проверяются правила перехода** (если нарушено – возвращается ошибка).  
   - При успешном изменении статуса генерируется **доменное событие**, которое:
     - отправляется через **WebSocket** всем участникам проекта (реальное время);
     - дублируется через **gRPC** (для возможного внешнего потребления).

5. **Уведомления в реальном времени**
   - Клиент (Vue.js) подключается к WebSocket-эндпоинту и получает обновления по задачам (изменение статуса, назначение, комментарии).  
   - В интерфейсе отображается всплывающее уведомление.

### Технические требования

#### Бэкенд (Go)
- **Веб-фреймворк**: `gorilla/mux` для REST.  
- **Аутентификация**: интеграция с Keycloak (валидация JWT, получение ролей).  
- **База данных**: PostgreSQL (миграции через `golang-migrate`).  
- **gRPC**: сервер на порту `50051` с protobuf-контрактом для уведомлений.  
- **WebSocket**: эндпоинт `/ws` с авторизацией через токен (в query или в первом сообщении).  
- **Архитектура**: чёткое разделение на слои (Domain, Application, Infrastructure, Interfaces).  
- **Тестирование**:
  - Unit-тесты для доменной логики и use-cases (с моками репозиториев).  
  - Интеграционные тесты для репозиториев (с реальной БД).  
- **Документация API**: Swagger/OpenAPI (генерируется аннотациями) – доступна по `/swagger`.

#### Фронтенд (Vue.js)
- **Фреймворк**: Vue 3 (Composition API) + Vite.  
- **Стейт-менеджер**: Pinia (опционально).  
- **Страницы**:
  - Вход/регистрация (редирект на Keycloak или встроенная форма с отправкой на бэкенд, который проксирует аутентификацию через Keycloak).  
  - Список проектов.  
  - Доска задач (канбан) с колонками, возможность перетаскивать карточки (drag-and-drop).  
  - Модальное окно создания/редактирования задачи.  
- **WebSocket-клиент**: подключение при входе, подписка на события, отображение уведомлений.

#### Инфраструктура
- **Docker Compose**: поднимает:
  - PostgreSQL;
  - Keycloak (с предварительно созданным realm и клиентом);
  - Go-бэкенд;
  - Vue-фронтенд (раздача статики через Nginx или dev-сервер).  
- **Переменные окружения** описаны в `.env.example` с обязательными и опциональными значениями.

#### Документация и спецификации
- В корне проекта папка **`/docs`** должна содержать:
  - **README.md** – общее описание, инструкции по запуску, ссылки на Swagger, gRPC-документацию.  
  - **ERD-диаграмма** (можно в виде текста или изображения) с комментариями по каждой таблице.  
  - **Архитектурный дизайн** (краткое описание слоёв, потоков данных).  
  - **Описание workflow** – как хранятся статусы и правила переходов.  
- Папка **`.opencode/`** должна содержать инструкции для AI-агента:  
  - `instructions.md` – общие принципы разработки, стиль кода, как запускать тесты.  
  - `spec.md` – бизнес-спецификация (сущности, сценарии).  
  - плагины (если нужны).  
- **Proto-файлы** лежат в `backend/proto/`.  
- **Swagger-генерация** интегрирована в Makefile.

#### Тестирование e2e (Playwright)
- Написать минимум **два e2e-сценария**:
  1. Регистрация пользователя, создание проекта, добавление доски, создание задачи и её перемещение по статусам (проверить, что правило перехода срабатывает).  
  2. Проверка реального времени: в одном браузере пользователь меняет статус, в другом (или второй вкладке) приходит уведомление через WebSocket.  
- Тесты должны запускаться в **headless** и **headed** режимах.

### Что должен предоставить кандидат по итогу

1. **Исходный код** всего проекта (монорепозиторий).

3. **Документация** в `/docs` (README, ERD, архитектура).  
4. **Инструкции для AI-агента** в `.opencode`.  
5. **Покрытие тестами** (unit + интеграционные + e2e).  
6. **Swagger** и **proto-файлы**.

### Критерии оценки

- **Работоспособность** – приложение запускается, все сценарии выполняются.  
- **Архитектура** – соблюдение DDD, чистота слоёв, использование интерфейсов.  
- **Качество кода** – нейминг, структурированность, обработка ошибок, логирование.  
- **Тесты** – наличие и осмысленность unit / e2e тестов.  
- **Соблюдение требований** – использование gorilla/mux, Keycloak, настраиваемый workflow.  
- **Документация** – полнота и понятность.  

Срок выполнения – **1 календарный день**.
