# Известные недочёты

Результат аудита проекта на соответствие [ТЗ](../тз.md) (15.08.2026). Все обязательные требования ТЗ выполнены; ниже — отклонения от буквы ТЗ и недочёты качества, упорядоченные по значимости. Ничего из списка не блокирует работу приложения.

## Отклонения от буквы ТЗ (некритичные)

1. **Нет папки `.opencode/plugins/`.** В ТЗ помечена как «плагины (если нужны)», т.е. опциональна. `instructions.md` и `spec.md` на месте.
2. **Unit-тесты лежат рядом с кодом**, а не в `backend/tests/unit/`. Это идиоматично для Go; структура в ТЗ обозначена как «рекомендованная». Интеграционные тесты — в `backend/tests/integration/`, как рекомендовано.

## Бэкенд

3. **Realm-роли Keycloak не участвуют в авторизации.** Роли извлекаются из `realm_access.roles` (`backend/internal/infrastructure/auth/keycloak.go`), но все проверки доступа построены только на project-scoped ролях из таблицы `project_members`. Любой аутентифицированный пользователь может создать проект (и станет в нём admin) — допустимая трактовка ТЗ («admin = создатель проекта»), но realm-роль `viewer` ни на что не влияет.
4. **Уникальность `position` статусов не гарантируется.** Проверка дублей позиций есть только при создании доски (`application/service.go`); в `CreateStatus`/`UpdateStatus` и в схеме БД (`migrations/000001_init.up.sql`) ограничения `UNIQUE (board_id, position)` нет — возможны статусы с одинаковым порядком.
5. **In-memory брокер событий** (`infrastructure/realtime/broker.go`): события не расходятся между репликами бэкенда, при переполнении буфера подписчика (64) старые события вытесняются — медленный клиент может потерять уведомления. Ограничение честно описано в `architecture.md`, предложен outbox.
6. **`TokenValidator` объявлен в `infrastructure/auth`**, из-за чего слой `interfaces` импортирует `infrastructure`. Правильнее вынести порт в domain/application.
7. **Access-log без HTTP-статуса ответа и request-id** (`httpapi/http.go`); уровень логирования зафиксирован на `Info` и не конфигурируется — `Debug`-записи никогда не пишутся.
8. **`swag` не зафиксирован в `go.mod`** — запускается через `go run ...@v1.16.4`, для регенерации Swagger нужна сеть.

## Тесты

9. **Интеграционное покрытие минимальное:** один тест (`tests/integration/postgres_repository_test.go`), покрыта примерно половина методов репозитория. Не покрыты: `UpdateStatus`, `DeleteStatus`, `UpdateRule`, `DeleteRule`, `UpsertMember`, `UpdateTask`, `ListTasks` и др.
10. **Тихий скип интеграционного теста:** при пустом `TEST_DATABASE_URL` тест пропускается — прогон без БД выглядит «зелёным».
11. **HTTP-слой почти не покрыт тестами** — только CORS-preflight и маппинг ошибок; роутинг, парсинг тел запросов и коды ответов REST-эндпоинтов не тестируются. gRPC — только валидация аргументов; сам стриминг событий не тестируется.
12. **Непокрытые ветки домена:** в `domain.ValidateTransition` — пустой целевой статус и переход «в тот же статус»; в `Service.TransitionTask` — целевой статус с чужой доски.
13. **`make test` не включает** `test-integration` и `e2e` — их надо запускать явно. CI-конфигурации нет.

## Фронтенд

14. **Частичное сохранение при редактировании задачи** (`frontend/src/views/BoardView.vue`, `saveTask`): поля задачи сохраняются (`updateTask`) до проверки правила перехода (`transition`). Если правило блокирует смену статуса, изменения полей уже применены, а пользователь видит только «Transition blocked».
15. **Токен в WS-URL не обновляется после refresh** (`src/api/realtime.ts`): долгоживущее соединение работает со старым токеном. Смягчено тем, что бэкенд переавторизует доступ на каждое событие.
16. **Нет отдельного события «назначение исполнителя»** — смена assignee приходит как общий `task.updated`; уведомление пользователь получает, но оно не отличимо от прочих правок задачи.
17. **Drag-and-drop на нативном HTML5 DnD:** работает только между колонками (порядок карточек внутри колонки не хранится) и не работает на тач-устройствах. Альтернатива — смена статуса через модалку — есть.
18. **Исполнитель и участник задаются ручным вводом Keycloak UUID** (`TaskModal.vue`, `ProjectsView.vue`) — на бэкенде нет эндпоинта поиска пользователей.
19. **Мёртвый код:** метод `taskflowApi.tasks()` (`src/api/taskflow.ts`) объявлен, но не используется — задачи приходят в составе `GET /boards/{id}`.

## Инфраструктура и документация

20. **Корневой `README.md` минимальный** (14 строк): нет описания стека, структуры репозитория, таблицы портов/сервисов. Подробный README находится в `docs/README.md`, как и требует ТЗ.
21. **E2e не запускаются одной командой:** в `playwright.config.ts` нет секции `webServer` — стек нужно поднять заранее (`docker compose up`). Задокументировано в `docs/README.md`.
22. **Стадия `test` в `backend/Dockerfile` не используется:** compose не указывает `target`, поэтому тесты при сборке образа не выполняются.
23. **В Makefile нет целей `lint`/`fmt`** и цели для копирования `.env.example → .env`.
